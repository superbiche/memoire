## Objectives (from the handoff, restated as testable deliverables)

1. `schema-pg/` — PostgreSQL DDL translating schema/0001-0012, additive
   discipline re-established (numbered files, applied-in-order, version
   table), pgvector extension installed and versioned from day one (no
   embedding schema — separate chantier).
2. `cmd/pgreplay` (or script) — drain-equivalent replay: raw/ envelopes →
   Postgres through the SAME NormalizeEnvelope semantics, so the raw
   files are the ground truth for both engines.
3. Parity harness — replays the same corpus into SQLite and Postgres,
   then diffs: row counts + content hashes per table class, and
   side-by-side results for the real injection/search query shapes.
   Ranking WILL differ (bm25 vs ts_rank): the harness RECORDS deltas
   (overlap@k, rank displacement) against a journaled regression
   threshold — parity assessment only, no ranking redesign (supplement
   open question 2 stays pending).
4. Standing-shadow loop (D152): the same harness re-run iteratively —
   delta re-replay + re-diff — becomes the R-9 rehearsal evidence once
   pointed at the HL3 shadow cluster; locally it runs against Podman
   `pgvector/pgvector:pg16`.

## Dual-engine posture (D157)

SQLite stays a first-class backend (release consideration: local-first
single-user deployments), Postgres/CNPG serves hub scale. Slice-5
execution introduces a store-layer DIALECT SEAM, not a driver swap; this
harness is therefore PERMANENT — the cross-engine conformance suite —
and schema/ + schema-pg/ evolve in lockstep under the same additive
discipline.

## Rehearsal loop design

    make pg-shadow-up          # podman run pgvector:pg16, apply schema-pg/
    make pg-replay             # replay raw/ (or a corpus copy) via pgreplay
    make pg-diff               # parity report -> tmp/pg-parity-<stamp>.md
    make pg-shadow-down

- Replay is idempotent (same dedup semantics as SQLite ingest) so the
  standing-shadow delta iteration is just "run replay again with the
  grown raw/ dir, re-diff".
- The diff report is the journaled evidence artifact: table-class counts,
  hash comparisons, query-shape side-by-sides, ranking-delta metrics,
  and an explicit PASS/FAIL against the thresholds.
- Corpus source: raw/ custody (ground truth per the handoff). The local
  loop may use the live raw/ read-only or a copy; the HL3 shadow uses
  the synced corpus.

## Cutover data model (two lanes; roles fixed by D159)

- COPY lane (full store, ids preserved): bulk row copy SQLite -> PG.
  THE flip-builder — the cutover database is rebuilt by a fresh
  clean-slate copy inside the window (D159). Also carries everything
  replay structurally cannot reconstruct: curated observation states,
  review log, derivation runs, source links, credentials, audit,
  project identity.
- REPLAY lane (events + raw observations + sessions): from raw/ custody
  through NormalizeEnvelope-equivalent ingest — the ground-truth-proving
  lane the handoff mandates; idempotent. Roles: standing-shadow
  monitoring (delta iteration, seconds per pass) and the disaster path
  (rebuild from raw custody if the store is lost). NOT the flip
  mechanism: derived artifacts and mutable columns do not travel
  through replay (first standing iteration measured -172 observations
  / -20 derivation runs / -276 source links after a 2h derive gap).

Tooling: single Go binary `cmd/pgshadow` with subcommands `apply` (DDL),
`copy` (bulk lane), `replay` (raw lane, `-delta` skip-list), `diff`
(parity report).

## Cutover recipe + go/no-go checklist (D159, operator-ratified 2026-07-21)

Recipe (window, ~10 min): quiesce -> drain-to-zero -> fresh full copy
into a re-applied EMPTY schema -> diff vs the frozen store, must be
EXACT (all tables, mutable columns included; any WARN above ranking is
NO-GO) -> flip MEMOIRE_BASE -> unquiesce.

Go/no-go checklist, black on white:

1. QUIESCE FREEZES DERIVATION, NOT JUST TRAFFIC: memoire service +
   derive timer + hourly sweep all stopped (precedent D144/D145/D151).
   Otherwise the derived-rows divergence class D159 eliminates recreates
   itself during the copy.
2. SAME-DAY REHEARSAL: a full-copy + EXACT-diff pass must have
   succeeded the same day, before the window opens (full recipe minus
   flip: quiesce -> copy -> exact diff -> unquiesce). The cutover then
   replays a playbook executed hours earlier on the same hardware —
   the strongest form of the R-9 dress-rehearsal condition.
3. Queue drained to zero and forwarder pending at zero before the copy
   starts (drain-to-zero, D147 addendum).
4. Injection-quality re-run vs the shadow completed BEFORE the window
   (D157/D158 ranking gate) — not inside it.
5. Fallback armed: the frozen SQLite file + raw custody stay untouched;
   flip-back is a config revert.

## Ranking parity thresholds (proposed, journal before first diff run)

- Search parity: for the top-10 of each probe query, overlap@10 >= 7 and
  the top-1 result present in the other engine's top-3; deltas recorded
  per query either way.
- Timeline/injection parity: EXACT row-set equality required (no ranking
  involved — deterministic ORDER BY on epochs/ids); any diff is FAIL.
- Counts/hashes: exact equality per table class; any diff is FAIL.

## Groundwork evidence (2026-07-20, local shadow on pgvector:pg16)

- DDL applies clean: 11 tables, 45 indexes, 2 governance triggers; probes
  green (guard fires with the exact message, tsvector search matches,
  both partial-predicate query shapes accepted, ON CONFLICT dedups).
- COPY lane on a frozen `.backup` of the live store (196,664 events,
  229k observations, 259k audit rows; 71s copy): parity diff ALL PASS
  across 11 table classes + timeline exact-set PASS
  (tmp/pg-parity-2026-07-20-frozen.md).
- Two design lessons the harness taught immediately:
  1. LIVE-STORE DRIFT: an unfrozen copy diffs dirty (15-row deltas from
     this session's own captures) — the harness detects it, validating
     the freeze -> drain-to-zero window discipline.
  2. COLLATION: SQLite BINARY vs Postgres locale collation order TEXT
     differently (paths, JSON punctuation) — an ordered running hash
     misreports pure sort-order differences as content divergence. Row
     hashing is therefore a MULTISET (per-row sha256 summed mod 2^256),
     order-independent by construction. Execution-time note: audit any
     app-level ORDER BY on TEXT columns at the dialect seam; consider
     LOCALE 'C' for the real cluster if SQLite-identical text ordering
     ever becomes contractual (today's read paths order by epochs/ids).
- SEARCH RANKING (the measured delta — CORRECTED in round 1): the first
  0-1/10 overlap measurement compared DIFFERENT candidate-set semantics
  (SQLite SanitizeFTS is OR-joined; the probe used plainto/AND). With the
  probe rebuilt on the same OR semantics the overlap re-measures ranking
  alone — see the post-repair parity report for the corrected numbers. As
  designed this is WARN, not FAIL — but the magnitude says engine-native
  ranking differs SUBSTANTIALLY on this corpus; the cutover-era injection
  quality assessment (claude-mem retirement gate pattern) should re-run
  against the shadow before flip. Journaled as the parity assessment's
  headline finding; ranking redesign stays out of scope (supplement open
  question 2).

## Replay-lane evidence (2026-07-20)

- Full raw custody replay into a fresh shadow: 225,037 files ->
  196,720 ingested + 28,317 duplicates collapsed + 0 FAILED (27m11s,
  one tx per envelope).
- Divergence vs a fresh live freeze: exactly the live tail — the
  surplus events' received_at starts at the replay's listing second
  (1784546618 vs start 1784546617). Convergence is by delta iteration,
  as designed.
- ONE content finding in 196,720: an envelope predating the received_at
  stamp got a replay-time fallback stamp (SQLite had drain-time). Fixed:
  the fallback is now the raw file's mtime (= the drainer's copy time).
  Impact ceiling: received_at is alert-only (D152); window queries never
  touch it.
- EXECUTION-TIME WORK (named, measured): the delta iteration must not
  re-read all 225k files (27 min/pass). DONE 2026-07-21 (branch
  slice-5-execution): `replay -delta` preloads the shadow's idempotency

  the shadow itself is the skip criterion) and skips present files with
  zero per-file DB round-trips. Live vs the HL3 cluster: 232,212 files,
  232,130 skipped, 82-event tail ingested, 0 failed, 23s.
